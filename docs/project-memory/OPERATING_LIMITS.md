## 高风险操作

- 连接真实 PLC、真实相机或会触发现设备动作的命令。
- 将密钥、模型、客户数据、运行日志或现场配置传到仓库外或网络位置。

## 工作节奏

- 大任务拆成小批次：探索、计划、实现、验证、记录。
- 每批只改必要文件，避免顺手重构无关模块。
- 开始修改前先确认 `git status --short`，识别已有用户改动。
- 读取和写入仓内文本文件默认使用 UTF-8；PowerShell 读写必须显式指定 `-Encoding UTF8`，脚本生成文本必须使用 UTF-8 写入，不能用系统默认 ANSI/OEM 编码处理中文文档、配置或界面文案。
- 完成一批后更新任务历史和动态记忆。
- 如需提交，提交信息必须说明相对上一版的变化：本次解决的问题、主要改动范围、关键验证结果；禁止使用无法说明差异的笼统信息，如 `update`、`fix`、`change`。

- 上下文即将耗尽或任务无法在当前会话完成时，必须把未完成任务、已改文件、验证状态、下一步命令写入 `HANDOFF.md`。

## 验证规则

- 模拟验证只能说明逻辑可能正确，不能替代真实程序或真实设备验证。
- 单个测试通过不等于整体成功；多文件、多功能改动必须跑集成测试或完整链路验证。
- 文档改动至少验证文件存在、路径正确、内容可读。
- 代码改动按风险选择验证：
  - 纯业务逻辑：对应单元测试 + 相关集成测试。
  - UI：构建主程序 + 实机启动观察或截图。
  - 启动/打包脚本：实际运行脚本并检查产物。
  - PLC/相机：优先安全模拟验证，再按用户同意连接真实设备验证。

## 代码重构替换规则

修改代码时必须严格遵守以下规则，不可违反：

1. 最小改动原则：只修改用户明确指定的功能部分，其他现有代码的逻辑、结构、命名、风格一律保持原样，禁止“顺手优化”或“重构周边代码”。
2. 替换优先：同一功能只能有一份实现。修改时必须先删除旧逻辑，再写入新逻辑。禁止保留注释掉的旧代码、废弃函数或备用方案。
3. 完整输出：说明代码变更时，必须输出修改后的完整函数或完整文件，禁止只输出片段或 diff。
4. 先删后写：输出新代码前，必须先列出【删除清单】，明确写出删除的函数、变量、import 或旧逻辑的行号和理由。
5. 零冗余：修改后必须清理未使用的 import、未调用的函数/变量、注释掉的代码块、功能重复的旧逻辑。
6. 禁止事项：绝对不允许保留注释掉的旧代码；不允许写临时/备用方案并存；不允许只输出片段；不允许在文件末尾追加新函数而不删旧函数；不允许使用 TODO/FIXME/HACK 等标记拖延清理；不允许改动用户未提及的现有代码逻辑。

代码修改任务必须按以下流程回复和执行：

1. 理解需求，定位需要替换的代码。如果需求模糊，先列出理解并等待用户确认，不要直接动手。
2. 输出【删除清单】，格式如下：
   - 删除 `xxx()`（第 X 行），理由：被新逻辑替代
   - 删除 `import xxx`（第 X 行），理由：不再需要
3. 输出【变更清单】，说明具体改了什么，并声明“未改动部分：除上述变更外，其余代码逻辑保持不变”。
4. 输出完整代码（完整函数或完整文件），代码中不允许有任何被注释掉的旧逻辑。
5. 输出【自检完成】，逐项确认：
   - [x] 仅修改了指定功能，未改动其他现有逻辑
   - [x] 已删除所有被替换的旧代码
   - [x] 已清理未使用的 import/变量/函数
   - [x] 无注释掉的废弃代码
   - [x] 同一功能无重复实现
   - [x] 输出为完整上下文，非片段

如果用户认为删除清单有误，只保留用户明确要求保留的内容。不要因为“以防万一”保留旧实现；优先保持干净替换，避免堆积历史逻辑。

## UTF-8 读写规则

- 以后读取和写入仓内文本文件默认使用 UTF-8。
- PowerShell 读取、追加、重写文本时必须显式指定 `-Encoding UTF8`。
- 生成脚本、配置、中文文档和界面文案时必须使用 UTF-8 写入，不允许依赖系统默认 ANSI/OEM 编码。
- 如果发现已有中文乱码，先确认影响范围，再用 UTF-8 一次性修正，不要继续追加新的乱码或中英混杂规则。
